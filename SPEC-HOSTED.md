# Hosted Measurement Protocol: Managed Inference Endpoints
### Project: Percentes. This document is the pre-registered protocol SPEC.md §6 requires before any hosted-provider data is collected.
### Status: drafted 2026-08-19, revised 2026-09-26, amended 2026-10-11 by HA1 as modified by HA3, and by HA3; pre-data. No provider data has been collected under this document.

## 0. Scope, subordination, and amendment log

This document specifies how the Percentes harness measures a managed inference endpoint (`target.hosted`). It is subordinate to SPEC.md v0.2: SPEC.md §6's Hosted targets subsection fixes which pins apply, which cannot be verified, and which run-validity gates are evaluable, and this document adds the numbers that paragraph defers. Where the two disagree, SPEC.md governs and this document is amended.

Every rate, duration, threshold, and coverage rule below is fixed here before collection. The SPEC.md §0 discipline governs: a configuration outside these numbers refuses to load under the §9 hosted profile, and a run missing a required artifact does not publish.

A hosted run is not a run of the SPEC.md §1 experiment (SPEC.md §6). It injects no fault and carries no service level objective (SLO), and the SPEC.md §1 topology gates do not apply to it. It characterizes the client-observed behaviour of one managed endpoint under a fixed open-loop load. The SPEC.md §9 verification disclosure, one author with merges not independently reviewed, applies to hosted collection unchanged.

## 1. The measurement

For a release, HA3 points 2 and 12 (§0) replace the target's path shape and the comparison scope below.

**Question:** for one model on one managed endpoint, what fraction of scheduled requests complete within the pinned client timeout, and what are the client-observed distributions of TTFT, end-to-end latency, and completion length, sampled across a fixed grid of times of day and day types?

**Target:** one provider, one model identifier, one endpoint, one account tier per run. The harness posts to `/v1/chat/completions` appended to the configured base URL, with streaming enabled. A provider that does not expose that path shape is out of scope for this document.

**Fault variant:** `none`. The harness has no authority over a provider's infrastructure, and no fault is injected.

**Comparison scope:** a characterization covers one provider-model pair. A comparison table across providers additionally requires the pointwise interval bands of SPEC.md §3, so no cross-provider comparison table publishes under this document.

## 2. Endpoint, model, and client host

For a release, HA3 point 7 (§0) replaces the single probe request below with the ten-request ceiling check, point 4 deletes the exclusion of a model that reasons on a separate field, and point 11 adds the account records.

- **Exact model identifier, recorded, no aliases.** The identifier sent on the wire (`target.model_name`) is recorded per run. An identifier the provider's published documentation describes as a pointer that can resolve to different underlying builds over time is ineligible, because the measurement would not name what it measured. Eligibility is checked against the provider's model documentation and recorded per run with the documentation URL and the retrieval date. Where the documentation does not state whether the identifier is fixed to one build, the identifier is recorded as stability-not-documented and the characterization publishes with that label.
- **Reported identifier.** Where a response carries a model identifier, it is recorded and compared with the expected one, per response. The expected identifier is the requested one, unless the probe below returns a different string and the provider's model documentation, recorded with URL and retrieval date, states that both names refer to one fixed build; the probe's string is then the expected value. Where the probe's string differs and the documentation is silent, the provider-model is recorded as identifier-not-documented and is not characterized. A run in which any response's reported identifier differs from the expected one publishes with the expected identifier and every distinct reported identifier, is excluded from pooled figures, does not count toward frame completeness (§4), and has its cell re-run.
- **Response shape, checked before characterization.** Before a provider's first run, one probe request is issued and the response shape recorded: the reported model identifier, which field of the streamed delta carries generated content, whether the model emits reasoning or analysis on a separate field alongside it, and which `finish_reason` values it returns. A content predicate tuned to one field scores a model that carries its output in another as empty_stream on every request. A provider-model whose content field the §6 predicate does not recognize is not characterized until a numbered amendment (§0), adopted before that provider's first measured run, extends the predicate to it, and the recorded shape publishes with the run. A provider-model whose probe shows reasoning or analysis on a separate field is not characterized under this document: the 256-token ceiling and the content-only predicate would then measure the client's budget.
- **Routing products excluded.** An endpoint documented to dispatch across several models or several providers carries no single pinned identifier and is not measured under this document.
- **Endpoint and account.** Recorded per run: base URL, the provider's declared region or point of presence, taken from the endpoint configuration or a response header where the provider exposes one and never inferred from latency or addressing, the account tier, and the provider's published status for the endpoint at run start and at run end. Routing behind the base URL is the provider's and is not controlled; the resolved peer address is recorded per request (§9).
- **Terms review.** Before a provider's first run, the provider's terms applicable to the account are reviewed for provisions on automated access, on publication of measurement results, and on republishing response metadata such as request identifiers, and the review is recorded with URL and retrieval date. A provider whose terms do not permit the planned traffic and publication is not characterized. Where the terms restrict republishing response metadata, the request identifier moves from the published JSONL artifact to a retained unpublished artifact.
- **Dedicated account.** The account and credential used for a characterization serve no other workload during the collection window, so recorded tier limits and 429 responses reflect this harness's traffic only; the run manifest records this.
- **Documentation snapshots.** Every documentation record in this protocol (model eligibility, terms, tier limits, endpoint status, incident history) carries a retained copy of the retrieved page and its SHA-256 content hash, alongside the URL and retrieval date. A documentation change, wherever this document tests for one, is a difference between the text this protocol records from a page at a later retrieval and the same text in the retained copy.
- **One client host per characterization.** All 12 cells (§4) run from one dedicated non-spot cloud instance, with its provider, region, instance type, image, and operating system pinned and published, and round-trip time (RTT) measured per run per SPEC.md §6. The run manifest records whether the client instance's cloud vendor is the measured provider or an affiliate of it. A characterization whose cells did not share one client host does not publish, because the grid would then measure the client alongside the endpoint.
- **Credentials.** The configuration carries only the environment-variable name (`target.api_key_env`). The key value is resolved at run start and is written to neither the configuration nor the run manifest.
- **One target per run.** A run addresses one endpoint and one model. Runs are never merged across endpoints, models, or account tiers.

## 3. Load profile (pinned)

For a release, HA1 as modified by HA3 point 5 (§0) replaces the single rate and duration below with the ladder, point 6 replaces the headroom rule with the ceiling rule, point 3 replaces the sampling bullet with the per-target body and credential, and point 7 replaces the input, output-ceiling and timeout pins with Shape S.

- **Rate: 0.5 requests per second, Poisson arrivals, open loop.** The rate does not rise with the account tier: a higher tier supplies headroom, and the offered load stays identical so runs compare.
- **Duration: 60 s warm-up, discarded, then a 1200 s measured window.** The warm-up matches the SPEC.md §1 pinned value. A request that opens a new connection inside the measured window carries its DNS (Domain Name System) lookup, connect and TLS (Transport Layer Security) handshake time in its client-observed TTFT. There is no fault instant and no cooldown phase. The generator drains, returning when every scheduled request has reached a terminal state or its timeout (SPEC.md §3), so censoring inside the horizon is administrative.
- **Expected sample budget: 600 scheduled requests inside the measured window.** Arrivals are Poisson, so the realized count is a random variable around that expectation and is published per run. Tail claims follow SPEC.md §7's policy against the realized count. At 600 completed samples the p99 order-statistic ranks under SPEC.md §7 are 589 and 599 (594 plus or minus 1.96 times 2.44, rounded outward); the interval exists only where the completed count is at least 381, and a per-cell p99 publishes only with that interval and its completed count.
- **Input: `load.input_length_tokens` pinned at 512.** The message content is the per-request prefix `cs-<seed>-<index>`, with the index zero-padded to six digits so the request body length is constant, then a space, then `tok ` repeated 512 times. The 512-repeat suffix is identical across every request. The content is determined by the run seed, the request index, the pinned length, and the instrument commit, all published per run, so it reproduces exactly.
- **Unique per-request prefixes**, per SPEC.md §6. Provider-side prefix-cache state is not verifiable (§6).
- **Distinct seed per cell.** `run.seed` is derived per cell with the dates (§4), so no two runs of a characterization repeat a request body.
- **Output ceiling: max_tokens=256, no output-length forcing.** ignore_eos is pinned false for hosted targets (SPEC.md §6) and is absent from the wire request.
- **Sampling parameters unset.** The request body carries model, messages, stream, and max_tokens. Temperature, top-p, and any other sampling control are absent, so each provider's defaults apply; they are recorded where the provider publishes them and reported as not verifiable where it does not. The body requests no usage object (§6).
- **Client: 30 s HTTP (Hypertext Transfer Protocol) timeout, zero retries, monotonic clock.**
- **Transport pinned to HTTP/1.1**, so one in-flight request occupies one connection and no two requests share stream-level flow control. The enforcing transport setting and a per-run assertion on the negotiated protocol are required instrument changes (§9). `load.connections` is pinned at 32; the client adds it to the rate-derived provision of 30 (two times the pinned 0.5 requests per second times the pinned 30 s timeout), so the idle pool holds 62 connections; concurrent connections are never capped.
- **Nominal demand from these pins: 30 scheduled requests per minute and 23,040 nominal tokens per minute** (512 configured input units plus the 256-token ceiling, at 30 requests per minute, before the per-request prefix). Nominal, because the realized prompt token count depends on the provider's tokenizer (§6).

**Headroom rule.** Before a provider's first run, every numeric limit the provider publishes for the account tier is recorded with the documentation URL and the retrieval date, and the per-token prices with the same. A run proceeds only where each of these holds: the pinned rate is at most half a published request-rate limit, per minute or per second as the provider states it; the nominal token demand above is at most half a published token-rate limit over the same window, the factor of two being the allowance for the provider's tokenizer (§6); a published daily request or token quota is at least twice the summed nominal demand of every run scheduled on that UTC day, warm-up included; a published concurrency limit is at least twice the pinned 30 s timeout times the pinned rate, the mean number of requests in flight when every request runs to the timeout; and a published burst limit is at least twice the pinned rate over the burst window the provider states. Before each run, the account's remaining balance or quota, where the provider exposes one, is recorded and must cover the run's nominal demand at the recorded prices, or the run does not start; it is recorded again at run end. Where a tier fails a test, or where the provider publishes no numeric limit for that tier, the provider is not characterized on that tier, and the recorded limits or their absence publish with the reason.

**Schema note.** The configuration schema carries four profiles. `experiment` pins the SPEC.md §1 phase durations and a two-replica topology, and `ac` pins the SPEC.md §8 reference rate of 20 requests per second; both require a positive fault-window duration and a replica count that a managed endpoint does not expose, the full SPEC.md §6 pin list, which §6 of this document lists as not verifiable, and the SPEC.md §4 SLO block, which §7 of this document does not apply to hosted data. `pilot` carries the numbers of the drafted HA2 pilot, and `release` carries the ladder, shape and caps of HA1 as modified by HA3 (§0); each refuses a value outside its pins. No profile expresses the single-rate run this section first pinned: HA1 supersedes that pin for a release.

## 4. Temporal sampling frame

For a release, HA3 point 9 (§0) replaces the collection-window length below and adds the per-route offsets, the concurrent-run record and the per-route re-run bound.

- **Grid: 12 cells.** Six start slots in UTC, at 00:00, 04:00, 08:00, 12:00, 16:00, and 20:00, each executed twice: once on a weekday (Monday to Friday) and once on a weekend day (Saturday or Sunday). Day type is the UTC calendar day of the slot start, and the six weekend draws must include at least one Saturday and at least one Sunday. One run per cell, so 12 runs and an expected 7,200 scheduled requests per provider-model characterization.
- **Dates and order fixed in advance.** The 12 date-and-slot pairs, their execution order, and the per-cell seeds are generated by a deterministic procedure from one master seed: eligible dates for each cell are enumerated in calendar order over the window, and each cell's date draw takes the SHA-256 of the master seed concatenated with the cell's label, reduced modulo that cell's eligible-date count; each cell's run seed for attempt 1 or 2 (§4 Re-runs) is the SHA-256 of the master seed concatenated with the cell's label, the attempt number and a fixed suffix, whose first 8 bytes read as a big-endian unsigned integer with the top bit cleared form `run.seed`. Where the resulting weekend dates violate the Saturday-and-Sunday rule above, an incrementing counter is appended to the master seed and the full schedule re-derived until they satisfy it, and the final counter value is committed alongside the master seed. The master seed and the resulting schedule are committed to this repository before the collection window opens. Changing a pair after the window opens is an amendment (§0).
- **Start tolerance: 15 minutes.** A run that starts outside its slot by more than 15 minutes is not that cell.
- **Collection window: 14 days.** All 12 cells complete inside one 14-day window, whose start and end dates publish with the characterization.
- **Completeness.** A characterization with fewer than 12 completed cells does not publish as a characterization. Its individual run artifacts publish as runs, labelled incomplete-frame.
- **Re-runs.** A cell whose run does not publish, or does not count toward frame completeness, for any reason in §2, §4 (start tolerance), §5, §7, or §9 is re-run at the next occurrence of the same cell inside the collection window. A re-run under this rule is not a change to a date-and-slot pair; the failed pair stays recorded in the manifest. A cell is attempted at most twice inside the window; a cell that fails twice leaves the frame incomplete. Both the failed attempt with its reason and the completed attempt are listed in the run manifest.
- **Drift inside the window.** The account tier's published limits and the model documentation are re-recorded at each run start, and, with the provider's published incident history for the endpoint, at window close. A change to the limits or the documentation during the window, as defined under §2 documentation snapshots, splits the pooled figures: the run at which the change was first observed and every later run pool apart from the runs before it, and the characterization names the change.
- **Incidents.** A cell collected while the provider published an incident for the endpoint is labelled with that status and stays in the frame.
- **Reporting.** Pooled figures publish with the per-cell table beside them.
- **Grid limits.** It is a UTC grid: it does not equalize local business hours across providers, and no claim about a provider's peak or quiet period is made from it. A cell's figures describe that dated run and carry no run-to-run variance estimate.

## 5. Outcome model and the treatment of 429

For a release, HA3 point 8 (§0) names the terminator of each request shape and the in-band error sub-lines, point 7 replaces the censoring paragraph, and point 16 replaces the setup-defect sentence with the blocks, ladder ends and stops.

The SPEC.md §3 three-state outcome model applies unchanged: every scheduled request ends completed, errored, or censored, only completions enter latency histograms, and failure rates are first-class per window. The six SPEC.md §3 error classes apply unchanged, assigned by failure stage and status code.

**HTTP 429: errored, class status_429, reported on its own line.** A delivered 429 terminates the request as errored in the SPEC.md §3 class status_429, assigned by status code; no cause is inferred from the code, the headers, or the provider's documentation. The status_429 count and rate publish per run and per cell beside the SPEC.md §3 error rate, in every denominator. A `Retry-After` value and every response header the provider documents as a rate-limit or quota header are recorded per request (§9) and change no class. `Retry-After` is never honored: retries are pinned at zero (SPEC.md §2), and honoring a back-off would convert the open-loop schedule into a closed loop.

**A nonzero status_429 fraction is a headline for its cell**, published with the tier limits recorded under §3. Poisson arrivals at half the published mean rate can still trip a limiter with no burst allowance, and a 429 can come from a limit dimension the headroom rule does not check or from provider capacity, so the figure publishes as observed 429s at the recorded tier and offered load, with no claim about which limit or which cause produced them.

**Other delivered statuses.** Every other non-200 status is class status_other with its status code recorded, whatever the provider's documentation calls it: a 503, 529, or 498 that the provider documents as overload or capacity stays in status_other and is visible through the per-status counts of §8. Where the provider's published documentation names a status code as rate limiting, quota exhaustion, or capacity shedding, that mapping is recorded per run with URL and retrieval date and publishes as an annotation beside the per-status counts; it changes no class. Redirects are not followed (SPEC.md §3), so a 3xx is a delivered status in status_other.

**Streams.** A delivered reset is reset; a stream that ends before the `data: [DONE]` frame (the terminator for OpenAI-compatible SSE) is malformed_stream, or reset where the transport reports one, per SPEC.md §3. The harness never infers completion from stream end; where a provider documents a different stream terminator, the run does not publish until the client recognizes it.

**Setup defects are caught before the window.** A pre-run probe from the client host (DNS resolution, TLS handshake, and the §2 response-shape request) gates the run start: a 400, 401, 403, or 404 on the probe, or an account-side limit the operator set, is a setup defect and the run does not start. Inside the measured window every 4xx other than 429 is status_other, counted and published with its status code. A run whose first response is a 400, 401, 403 or 404, or in which any response is a 401 or 403 or one the provider documents as an account-side limit the operator set, is a setup defect: it does not publish and its cell is re-run. A run in which no request completes publishes with hosted-G6 marked failed and its outcomes split by class (§8).

**Failures before a status.** A dial, DNS, or TLS failure before any response is errored under SPEC.md §3 in class connect, or reset where errors.Is(err, syscall.ECONNRESET) holds, with the Go error string recorded per request. It is a competing terminal event on the §8 incidence curve, counts toward the §8 conditional-percentile trigger, and stays in the error rate; the connect and reset counts publish on their own lines, attributed to neither side, because a refused dial or a failed handshake at the provider's edge is not distinguishable by the client from a fault on its own path. A run whose connect fraction exceeds 1 percent publishes with that fraction as a labelled headline for its cell and with that run's loopback canary result (SPEC.md §2) beside it; the run is withheld only where G2 (§7) fails.

**Censoring.** No terminal event by the pinned 30 s timeout is censored at that timeout, with its observation time, per SPEC.md §3.

The per-request HTTP status code is recorded in the run artifact (§9).

## 6. Pins: applied, and not verifiable

For a release, HA3 point 7 (§0) replaces the output-ceiling, input-length and timeout items of the applied list, point 3 replaces the sampling pin, and point 4 replaces the last two sentences of the tokenizer-and-usage paragraph.

This section restates SPEC.md §6's hosted-target lists and adds this document's own pins. Unverifiable items publish as unverifiable.

**Applied unchanged, all client-side:** max_tokens=256 as an output ceiling; fixed input length; the pinned prompt body with unique per-request prefixes; open-loop arrivals at the pinned rate; client HTTP timeout 30 s; zero retries; monotonic clock; the SPEC.md §2 client-validity gate; the single pinned HdrHistogram configuration (SPEC.md §3); the SPEC.md §3 three-state outcome model and estimator. Recorded per run: endpoint URL, requested model name, client placement, RTT.

**Added by this document, and pinned here:** the request rate and arrival process, the warm-up and measured-window durations, the transport protocol and connection figure, the per-cell seeds, the sampling grid and its tolerances, the collection window, the client host, the headroom rule, and the treatment of 429 and the probe rule of §5.

**Not applicable or not verifiable against a hosted endpoint:** ignore_eos and any output-length forcing; the model weights and revision behind the identifier; KV (key-value) cache budget; prefix-caching state; continuous-batching verification; serving-stack version and image digest; scheduler settings; CUDA (Compute Unified Device Architecture) graph enablement; GPU (graphics processing unit) SKU (stock-keeping unit), driver, and clock and power fingerprints; the Kubernetes, CNI (Container Network Interface), dataplane, kube-proxy, and node-monitor-grace-period pins; per-replica request counters.

**Tokenizer and usage.** The realized prompt token count and the realized completion token count are the provider's, produced by a tokenizer this protocol cannot pin or inspect. The pinned request body requests no usage object, so a provider-reported completion token count is available only where the provider emits one unrequested; where it is emitted it is recorded and published as its own distribution, and where it is absent that count publishes as not verifiable. The body is pinned flat across providers: requesting a usage object is a change to it, adopted as a numbered amendment (§0) before any data the change could affect is collected, never decided per provider after the target is known.

**Content events.** An SSE frame counts as a content event only where its delta carries a non-empty content string; the predicate in this provider-independent form is in the instrument, and carrying the per-provider response shape recorded under §2 is a required instrument change (§9). A stream that reaches the [DONE] terminator with no prior content event is errored, class empty_stream; a stream that ends any other way with no content event is reset or malformed_stream (SPEC.md §3). TTFT is timestamped at the first content event, so it is time to first generated token only under that predicate.

**Receive path.** SPEC.md §2's receive-path caveat applies in full and is aggravated here: client timestamps are taken when the read loop observes a frame, the network path is longer than a same-zone cluster path, and neither the provider's own TTFT histograms nor its event-coalescing behaviour is observable. The SPEC.md §2 loopback canary runs in every run and bounds the client host's own read-loop lag per window; the margin between client-observed and provider-side timing stays unmeasured, and every hosted timing is labelled client-observed.

## 7. Run validity and the reported criterion

For a release, HA3 point 7 (§0) makes hosted-G6 completion within the 30 s deadline, and point 13 fixes its interval per step and per cell.

**No SLO transfer.** The SPEC.md §4 SLO derives its end-to-end threshold from a forced 256-token budget (1000 ms plus 256 tokens at a 20 tokens-per-second floor, rounded up to 14 s), which hosted requests do not carry. Neither SPEC.md §4 threshold is applied to hosted data, and no hosted SLO is defined here. Latency publishes as distributions with no pass bar.

**Evaluable gates: G2 and hosted-G6.** Of the SPEC.md §10 gates, only these two are evaluable against a hosted target (SPEC.md §6). G1, G3, G4, G5, and G7 are reported as not applicable, never as passed.

- **G2, client validity, run-failing.** The SPEC.md §2 numbers unchanged: send skew (actual minus intended dispatch) p99 at most 5 ms and max at most 50 ms, zero scheduled-but-never-dispatched requests, client CPU (central processing unit) at most 70 percent sustained over any 5 s window, and Go garbage-collection pause p99 under 1 ms during the measured window. A criterion the run could not measure does not pass. A G2 failure means the numbers describe the client, so the run does not publish and its cell is re-run.
- **Hosted-G6, completion within timeout.** Completion-within-timeout is the fraction of the measured window's scheduled requests that complete before the pinned 30 s timeout (SPEC.md §6). The timeout runs from actual dispatch; reported latency is rebased to intended dispatch, so a counted completion can show up to 30 s plus the G2 skew bound of 50 ms. A hosted run has no pre-fault baseline window, so the measured window is the evaluation window. Hosted-G6's verdict is the point estimate over all scheduled requests against 0.99, the number SPEC.md §10 pins for G6, its baseline-goodput gate, carried over per SPEC.md §6; this document derives no hosted-specific threshold. It publishes per run and per cell with this definition attached and a 95 percent binomial (Wilson) interval at the realized denominator; the fraction over scheduled requests excluding connect and reset outcomes publishes beside it with its own interval, and the per-class error rates (§8) publish beside both. It is a property of this workload and timeout: completion within timeout depends on realized output length and the provider's decode rate as well as on availability, and it publishes beside the completion-length distribution (§8).

**Hosted-G6 is reported, never run-invalidating.** A hosted run whose completion-within-timeout falls below 0.99 publishes with the gate marked failed (SPEC.md §6).

## 8. Reporting

For a release, every figure below publishes per ladder step, and HA3 point 13 (§0) fixes the intervals and bands.

Per run and per cell, over the measured window:

- **Completion-within-timeout** with its numerator and denominator, the SPEC.md §3 error rate with its split into the six SPEC.md §3 classes (status_429, status_other, reset, connect, empty_stream, malformed_stream), the censored rate, and the count per delivered HTTP status code, each on its own line over the same scheduled-request denominator, so completion, error, and censored sum to one; the status_429 rate is observed under the pinned zero-retry client.
- **Aalen-Johansen completion-incidence curve** over all scheduled requests, with n and the SPEC.md §3 quantile-refusal rules, published as descriptive point estimates. The curve does not decompose competing events by error class; the per-class rates above carry that split.
- **TTFT and end-to-end distributions**, completed-only, labelled conditional on completion, from the pinned HdrHistogram configuration. Where the error-plus-censored fraction exceeds 5 percent, the SPEC.md §3 conditional-percentile rule applies and the incidence curve accompanies the percentiles.
- **Completion length as a distribution**: the client-side content-event count per completed request, labelled as content events under the §6 predicate, and the provider-reported completion token count where the response carries usage (§6). Content-event counts for errored and censored requests are in the §9 artifact and publish as their own per-outcome distribution.
- **Inter-chunk latency** as pooled per-window histograms of gaps between successive content events, labelled inter-chunk, never inter-token.
- **Throughput** as completions per second.

Pooled figures across the 12 cells publish with the per-cell table (§4); they are computed over all scheduled requests of the 12 cells and describe those runs, estimating no average day and no provider-wide rate. Where the §4 drift rule splits the window, each side pools separately, labelled with its cell count and date range. No pooled figure is published for a provider-model whose frame is incomplete.
